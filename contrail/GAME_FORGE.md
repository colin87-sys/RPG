# GAME_FORGE — Autonomous High-Quality Game Build Protocol (v2.1: procedural-first, seed-pack aware)

```
MODE: procedural      # default. Set "extended" in the idea card to enable optional generators (Appendix D)
```

**What this file is:** a self-contained operating manual for an AI coding agent (built for Claude Code with sub-agents). The human supplies a game idea. This file tells you, the AI, how to build the entire production kit (rules, spec, style bible, look-dev lab, test harness, reviewer, state files) with delegated agents, prove it works, and then run a long autonomous build that ends in a polished, playable game.

**In `procedural` mode (default) the whole game is produced by code:** no API keys, no third-party logins, no image/3D/audio generators, no MCP servers beyond what ships with Claude Code, no downloaded assets, no CDN links. Geometry, textures, sky, water, VFX, UI art, fonts, sound effects and music are all generated by code and verified by rendering them and looking at the result.

It generalises a process that produced a 36-hour autonomous game build. The lessons that made that work are baked in, adapted for a world where the agent cannot call an image generator.

---

## 0. For the human: how to use this

**You need:** Claude Code (already signed in), Node 20+, and git. That's it. Optional: ffmpeg (nicer timelapse), and a machine with a real GPU (only needed to measure true fps).

1. Put this file in an empty project folder.
2. Start Claude Code in that folder and send:

```
Read GAME_FORGE.md and follow it end to end. Do not ask me questions.

IDEA CARD
One-liner: <the game in one sentence>
Feel / vibe: <optional: 3-5 adjectives, e.g. "fast, painterly, arcade, readable">
Reference games (mechanics/feel only): <optional names>
My notes / analysis reports: <optional paths or pasted text>
Run length: <optional: e.g. 12h, 24h, 36h; default 24h>
Must-have: <optional>
Must-not-have: <optional>
```

Only the one-liner is required. Every blank is filled by a default (Section 4) and logged in `Docs/DECISIONS.md`.

3. **Biggest optional quality lever (no login needed):** drop 5-15 images you like (screenshots, concept art, mood boards) into `Docs/refs/owner/` before you start. The agent treats them as the highest-priority visual anchors. Without them the agent works from written principles and its own look-dev lab, which works but has a lower ceiling.
4. Override any decision or look pick at any time by writing `Docs/OVERRIDE.md`. The agent queues rework.
5. To end the run: request the wrap-up message (Section 10), then create `.claude/ALLOW_STOP` (Appendix B.10).

## 1. Prime directive (for the AI)

You are the **Director**. You do not build the game alone. You plan, delegate to focused agents, verify with evidence, and integrate.

Non-negotiables:

- **Never ask the owner a question.** Decide, write the decision and reason to `Docs/DECISIONS.md`, continue.
- **You cannot judge visuals you have not looked at.** Never describe, score or claim anything about an image you have not opened in this session. AI-built games look like slop mainly because the builder never sees the output. The render-capture-look loop (Sections 7, 9, 12) is mandatory.
- **You do not grade your own work.** A fresh-context Reviewer agent judges captures.
- **You cannot hear.** Audio is verified numerically and by spectrogram, and always labelled `pending owner review`.
- **Anything that matters is written to a file immediately.** Context will be compacted many times. If it is not in a file, assume you will forget it.
- **Always playable.** From the first playable milestone on, the gold path works at every commit.
- **Small and polished beats big and rough.** Cut scope before cutting quality.
- **Zero-dependency rule (procedural mode):** do not sign in to anything, do not request or store keys, do not call external APIs, do not hot-link. Allowed network use: `npm install` of open packages and `npx playwright install chromium`. The shipped game makes **zero external network requests**.
- English for code, docs, logs and commits (unless the idea card says otherwise).
- Work only inside the project folder. No pushes to remotes, no posting. Never print or commit secrets (there should be none).

Read order after any start, restart or compaction (once `CLAUDE.md` exists it repeats this):
1. `CLAUDE.md`
2. `Docs/PLAN.md`, `Docs/TODO.md`
3. Last three entries of `Docs/DEVLOG.md`, and `Docs/STATS.json`
4. `Docs/STYLE_BIBLE.md`, `src/style/tokens.ts`, and the boards in `look/approved/` (plus `Docs/refs/owner/` if present) before any visual work
5. Run `date`.

Before `CLAUDE.md` exists, read this file and `Docs/PLAN.md` (if present).

## 2. Why this works (principles to preserve)

1. **Layered documents, each with one job:** rules (`CLAUDE.md`), task/spec (`TASK.md`), mechanics numbers (`DESIGN.md`), look (`STYLE_BIBLE.md` + tokens + approved boards), lessons (`PIPELINE_LESSONS.md`), messages to paste (`KICKOFF.md`).
2. **Pictures, not adjectives, define the look.** In procedural mode the pictures are the **Look-Dev Lab boards** rendered by the same code as the game, frozen as `look/approved/`. Because concept and game share code, drift is measurable.
3. **Numbers, not prose, define the mechanics.**
4. **Acceptance is a table with testable pass conditions,** P0/P1/P2.
5. **Ordered scope with an explicit out-of-scope list.**
6. **Milestones with gates;** the game stays playable at each.
7. **A test harness gives the agent eyes and a pulse:** deterministic captures, gold-path driver, machine-readable results.
8. **Independent review with calibration,** using **paired comparison** (A vs B) because it is more reliable than absolute scores.
9. **Prior failures are short rules** with the fix.
10. **Hard budgets:** perf, bundle size, time, and attempt caps (no money to spend in procedural mode).

## 4. Phase 0 — Intake & decisions

### 4.1 Concept Card
Create `Docs/CONCEPT_CARD.md` from the idea card. Expand it yourself; do not ask.

- Working title (original), one-liner, genre, camera, core loop (one paragraph)
- **The 60-second experience** and **the 10-minute experience**
- Win/lose/progression model, target session length
- Three signature moments (what a trailer would show)
- Scope tier: **Slice** (default): one polished, complete loop with a beginning and a satisfying end state
- **Art direction that suits procedural generation** (pick one and commit): stylised geometric / low-poly-with-gradient-lighting / neon-vector / painterly-toon (ramp shading + outlines) / SDF-blobby-organic / voxel-ish. Avoid photoreal humans, faces, realistic animal anatomy and long cloth/hair simulation: procedural code does not sell those. Silhouette-driven, light-driven, particle-driven looks do.
- Three look-keywords the Reviewer will grade against
- Explicit out-of-scope list (at least 8 items)

### 4.2 Default decisions (log each to `Docs/DECISIONS.md` with reason)

| Decision | Default |
|---|---|
| Engine | **Web + Three.js** (via npm + Vite). Unity/Blender are excluded in procedural mode because they need editors and extra tooling |
| Language | TypeScript if it stays low-friction, else plain JS modules |
| Rendering | Fully procedural: parametric geometry, SDF/marching-cubes for organic forms, shader-generated textures, code-drawn UI |
| Run length | 24h unless stated |
| Scope | Slice |
| Perf target | 60 fps on a mid-range laptop GPU at 1080p; draw calls, triangles and bundle size budgets in `TASK.md` |
| Fonts | System font stack, or a bitmap/SDF font drawn to canvas by code. No web-font downloads |
| Audio | Web Audio API synthesis (SFX and generative music), no samples |
| Third-party assets | None in procedural mode |

### 4.3 Environment audit (`Docs/ENV_AUDIT.md`)
Check and record: Node and npm versions, git, ability to `npm install` (network), ability to `npx playwright install chromium`, whether headless WebGL works (try the flags in 14.1), ffmpeg (optional), real-GPU availability (for fps). For each gap, name the fallback (e.g. no ffmpeg: HTML slideshow timelapse; no real GPU: report relative frame time, labelled). Never block; route around and log.

### 4.4 Reference-game mode (only if the idea card names games or supplies notes)
- Other games are sources of **mechanics numbers, pacing, camera behaviour, readability principles, HUD hierarchy**, never assets, names, characters, logos or layouts.
- The Reference Analyst writes `Docs/refs/PRINCIPLES.md` (see W1). Anything from general knowledge is marked `assumption: tune in playtest` if the number is uncertain.
- The result must be an original game: original title, art and names. Log the "inspired-by, not clone" decision.

### 4.6 Seed pack (if `IDEA_CARD.md` and `Docs/seed/` exist)
The owner has already done Phase 0 and W1 groundwork. Do not restart it:
- `IDEA_CARD.md` is the idea card; skip decisions it already makes.
- `Docs/seed/CONCEPT_CARD.md`, `DESIGN_SEED.md`, `STYLE_SEED.md` are owner-approved starting points. Copy them to `Docs/CONCEPT_CARD.md`, `Docs/DESIGN.md`, `Docs/STYLE_BIBLE.md` and extend them (W2/W4). Numbers tagged **[A]** are assumptions to tune in scripted playtests; **[O]/[R]** lines must be verified against the references.
- `Docs/refs/` (`owner/`, `owner_refs.md`, `ANALYSIS.md`, `motion/`, `SOURCES.md`) is a finished W1. The Reference Analyst's job becomes **verification and extension**: a fresh agent opens every image and the motion contact sheets and frame sequences, corrects errors, and logs corrections in `Docs/DECISIONS.md`.
- **Copyright guardrail:** everything under `Docs/refs/` is a private third-party style reference. It must never appear in `src/`, `public/`, `dist/`, generated boards, or any published repo. Add `npm run refcheck`: hash every file in `Docs/refs/` and fail if any hash appears in the built output (P0 acceptance row).
- **Video note:** Playwright's bundled Chromium cannot decode H.264 MP4s. Use the pre-extracted frame sequences in `Docs/refs/motion/frames/` (about 15 fps) and the contact sheets; do not try to play the MP4s in the harness.
- The Reviewer compares captures to the owner references **by relationship** (temperature range, HUD layout, effect readability, silhouette read), never by pixel similarity.

## 5. Agent roster

You delegate with sub-agents (the Task/agent tool). Run independent lanes in parallel. Each agent gets: one lane, one deliverable, input files, a verification step, and a result path. Prompt stubs are in Appendix A.

| Lane | Owns | Output |
|---|---|---|
| **Director / Integrator** (you) | Project scaffolding, integration, git, state files | Root, `Docs/` |
| Look-Dev Director | The Look-Dev Lab, variant boards, `look/approved/` | `lab/`, `look/` |
| Reference Analyst | Written principles, owner-image notes | `Docs/refs/` |
| Spec Writer | `TASK.md`, `DESIGN.md`, `STYLE_BIBLE.md`, `tokens.ts` | `Docs/`, `src/style/` |
| Harness Engineer | Debug API, capture, gold path, perf, network check, audio check, contact sheets | `src/debug/`, `tools/` |
| Lessons Miner | `PIPELINE_LESSONS.md` from supplied notes + Section 14 | `Docs/` |
| Entities lane | Hero, enemies, obstacles: parametric builders | `src/gen/entities/` |
| World lane | Terrain, sky, water, props, atmosphere | `src/gen/world/` |
| UI lane | HUD, menus, icons (SVG/canvas), bitmap font | `src/gen/ui/` |
| VFX lane | Particles, trails, shaders, post-processing | `src/gen/vfx/` |
| Audio lane | Synth SFX, generative music, mixer | `src/gen/audio/` |
| Content lane | Text, tuning tables, names | `src/data/` |
| **Reviewer** (fresh context every time) | Judges captures, files defects | `Docs/reviews/` |
| **Red-Team** (fresh context) | Reads the kit as a new agent | `Docs/KIT_REVIEW.md` |

Rules:
- **One owner per shared resource.** Only the Integrator edits the main scene wiring (`src/main`, scene composition, build config) and runs git. Lanes deliver modules with a small manifest (`*.entity.json`: name, polygon count, bounding size in metres, palette tokens used, seed) and append to `Docs/INTEGRATION_QUEUE.md`.
- A lane may write and test code for its own folder; the Integrator wires and runs the harness.
- Every agent returns: files written, verification evidence (capture or log paths), open issues. No evidence means not finished.

## 6. Phase 1 — Kit generation (W1-W8, in parallel)

### W1 — Reference anchors (no downloads)
**If a seed pack exists (Section 4.6), W1 is already done: verify and extend it instead of rewriting.**

1. **If `Docs/refs/owner/` has images:** the Reference Analyst opens each one and writes `Docs/refs/owner_refs.md` with one entry per image: `what_to_take_from_it` (one specific, testable lesson: palette logic, silhouette, lighting direction, depth layering, HUD hierarchy). These outrank everything else.
2. **Always:** write `Docs/refs/PRINCIPLES.md`: for the genre, camera and art direction, list concrete visual and gameplay principles with reasons (readability of threats, depth cues, colour-coding rules, motion feel, HUD hierarchy, difficulty pacing). For named reference games, capture mechanics numbers and feel; mark uncertain figures `assumption: tune in playtest`. Include a `rejected` section of looks to avoid (default-material grey, saturated primaries, flat unlit shapes, random palettes).
3. Acceptance: every entry has a specific `what_to_take_from_it`; nothing vague like "nice style".

### W2 — Style bible + tokens (single source of truth)
- `Docs/STYLE_BIBLE.md`: palette with hex and 60/30/10 split per scene, key-light direction, rim light, ambient and fog colours, silhouette and shape language, shading model (ramp/toon/PBR-lite), outline rules, scale table, VFX language, UI language, gameplay colour coding, **Keep / Upgrade / Avoid**, **Rejected**.
- `src/style/tokens.ts`: the same values as code (palette, light direction, fog, ramp textures generated by code, outline width, UI colours). **All game code imports tokens; no hard-coded colours elsewhere.** The bible and tokens must match; the Reviewer checks this.

### W3 — Look-Dev Lab (replaces concept generation)
The lab is a set of pages under `lab/` that render **boards** using the same procedural builders as the game.

Boards per subject:
- **Hero/entity:** five angles, close-up, a **black silhouette test**, and a scale line-up next to a 1.8 m reference figure or unit cube
- **Enemies/obstacles:** line-up at true relative scale beside the hero
- **Environment:** vista at 3 times-of-day or 3 palettes; foreground/mid/background layers visible
- **HUD/menu:** mockup built in the real UI code, with gameplay-critical colour coding
- **VFX strip:** key frames of hit, pickup, trail, explosion/peak effect
- **Palette/light board:** swatches, lit spheres under the key/rim/ambient setup

Process:
1. For each subject, produce **3 variants** (A/B/C) by changing parameter sets (palette, lighting, shading model, proportions), not by rewriting code.
2. Capture each board (Section 7 tools), open the images, and build one side-by-side review page.
3. A fresh Reviewer ranks A/B/C by **paired comparison** with specific reasons against the style bible, `PRINCIPLES.md` and any owner refs.
4. Take the winner, then run a **consistency pass**: unify key-light direction, palette, outline weight, shading ramp, and detail density across all subjects so they read as one family.
5. Freeze: save boards to `look/approved/*.png` and parameter files to `look/approved/*.json`; update `tokens.ts`.
6. Write `look/selection.json` (Appendix B.5). Status: `pending owner review`.

Later, every in-game capture with a story camera is compared against its approved board.

### W4 — Spec
Write `Docs/TASK.md` and `Docs/DESIGN.md` from Appendix B.1-B.2. Non-negotiable: P0/P1/P2, an acceptance table with a testable pass condition and test method per row, an out-of-scope list (8+ items), milestones with gates, budgets (fps, draw calls, triangles, bundle size, memory, **zero external requests**), and `DESIGN.md` with every gameplay quantity as a number.

### W5 — Test harness (built before any feature work)
Node scripts using Playwright (Chromium) against `vite preview`, plus an in-page debug API. Deliverables (contract in Appendix C):
- `window.__game` debug API: `setSeed`, `setTime`, `step(n)`, `setCamera(name)`, `state()`, `capture()`; fixed timestep in deterministic mode
- **Story cameras**: named presets for hero close-up, environment vista, combat/peak moment, HUD, menu/title
- `npm run capture`: PNGs per story camera at chosen times
- `npm run contact`: contact sheet built by rendering an HTML page of the images in Playwright and screenshotting it (no image library needed)
- `npm run goldpath`: scripted play-through of the core loop, non-zero exit on failure
- `npm run perf`: median/1%-low frame time and draw calls
- `npm run netcheck`: loads the built game and fails if any request leaves localhost
- `npm run refcheck`: fails if any file from `Docs/refs/` appears in the built output (only when a seed pack with third-party references exists)
- `npm run audiocheck`: see W8
- `checks.json` writer (atomic)

### W6 — Lessons seed (`Docs/PIPELINE_LESSONS.md`)
Mine any supplied notes into short rules (problem, cause, fix, 1-3 lines). Always merge Section 14. Keep a "Things that cost hours" section that the run appends to.

### W7 — Rules and state
`CLAUDE.md` from B.6; state files from B.7; `Docs/KICKOFF.md` from B.8; hooks from B.10.

### W8 — Procedural audio plan
- SFX recipes (oscillator + noise + filter + envelope): hit, pickup, whoosh, explosion, UI click, warning, level-up. Parameterised so variations are cheap.
- Generative music: layered loops (bass pulse, arpeggio, pad, percussion from noise) with an **intensity parameter** that fades layers in/out with gameplay. Fixed key and tempo from `DESIGN.md`; simple chord progressions; humanised timing.
- Mixer: master limiter, per-bus gain, ducking for important cues.
- **Verification without ears:** render each sound and loop with `OfflineAudioContext` inside Playwright, then check numerically (peak <= -1 dBFS, no clipping, RMS within target range, DC offset near zero, loop seam continuity) and produce a **spectrogram PNG** the Reviewer opens. Mark audio `pending owner review (not audible to the agent)`.

## 7. Phase 2 — Harness proof and Reviewer calibration

1. **Stub game:** placeholder player, ground, HUD label, one scripted loop, one synth beep. Run the capture, contact sheet, gold path, perf, netcheck and audiocheck. Fix the harness, not the stub.
2. **Reviewer calibration by paired comparison** (Reviewer is a fresh agent with only the rubric and images):
   - Render the same test scene twice: **naive** (default materials, random colours, flat light) and **art-directed** (tokens, key/rim light, fog, ramp shading). The Reviewer must rank art-directed higher and give correct reasons.
   - If `Docs/refs/owner/` exists, also check that owner refs score above the naive render.
   - Give a capture with a deliberate defect (clipped silhouette, low-contrast HUD); the Reviewer must find it.
   - If ordering is wrong or comments are vague, rewrite the rubric/prompt and rerun.
3. Save results to `Docs/reviews/calibration.md`.

Exit only when all pass.

## 8. Phase 3 — Kit red-team and freeze

1. Spawn a Red-Team agent with no prior context. Prompt: "You are a new agent joining with only `Docs/`, `CLAUDE.md`, `look/` and the harness. List everything ambiguous, contradictory, missing or untestable, and the 10 most likely ways an autonomous procedural run would go wrong or look mediocre."
2. Patch the kit; record in `Docs/KIT_REVIEW.md` what was fixed and what was consciously accepted.
3. Verify: every acceptance row has a pass condition and test method; every milestone has a gate; read order points to files that exist.
4. Commit. From now on the harness, hooks and gold-path driver change **only between milestones, with a commit**.
5. DEVLOG: "Kit frozen".

## 9. Phase 4 — Long build

Operate under the generated `CLAUDE.md`. Default milestone ladder:

| Milestone | Content | Gate |
|---|---|---|
| **M0** Foundation | Vite project builds and runs, harness live, placeholder loop | Harness passes on the real project; zero console errors; netcheck clean |
| **M1** Playable core | Core loop playable start to end with placeholder art; gold path passes | Gold path passes; fps measured |
| **M2** Look lock | Hero, one environment and HUD at final-look quality, matching `look/approved/` | Reviewer paired comparison: in-game beats the naive baseline and matches boards; avg >= 7 on look axes |
| **M3** Content breadth | Remaining entities, environments, obstacles/enemies, progression | P0 acceptance rows pass |
| **M4** Peak moment | Boss/finale/signature moments with VFX and audio | Reviewer >= 7 on peak-moment captures |
| **M5** Polish | Juice (hit-stop, shake within limits, trails, transitions), audio mix, onboarding, menus, difficulty tuning | P0+P1 pass; perf budget met |
| **M6** Ship candidate | Bug bash, final captures, static build, report | Definition of done (Section 16) |

Each milestone:
1. Plan in `PLAN.md`; queue tasks in `TODO.md`.
2. Delegate lanes in parallel; modules flow through `INTEGRATION_QUEUE.md`.
3. Integrator integrates in batches, then runs the harness (gold path, captures, perf, netcheck, `checks.json`).
4. **Visual loop, every time visuals change:** capture -> open the image -> compare side by side with the approved board -> one-line critique in `DEVLOG.md` -> fix -> recapture.
5. Spawn the Reviewer on the milestone's captures; defects go to `Docs/reviews/<milestone>.md` (Appendix B.9) and into `TODO.md`.
6. Gate check; commit with a message that says what changed; DEVLOG.
7. If a change breaks the gold path and the fix is not obvious within 20 minutes, revert and re-queue.

Cadence:
- Commit every 30-60 minutes.
- DEVLOG at every milestone, every recovered failure, and at least hourly.
- `STATS.json` hourly (elapsed time, commits, lines of code, modules attempted/accepted/rejected by lane, bugs fixed, fps) and commit.
- Progress captures after every significant change and at least every 5 minutes of real time on the feature in progress, saved to `Docs/progress/<feature>/` with UTC timestamps.

When `TODO.md` is empty: run the full acceptance test, queue fixes for the lowest-scoring areas, continue. **Do not end the session on your own.**

## 10. Phase 5 — Wrap-up

Produce:
- `npm run build` output that runs from a clean clone with a static server, with **zero external requests** (netcheck) and zero console errors
- `Docs/REPORT.md`: what was built, acceptance results with evidence links, Reviewer scores, perf numbers, known issues, what was cut and why, next steps
- Final story-camera captures and contact sheet
- Timelapse from `Docs/progress/` (ffmpeg if present; otherwise a self-contained HTML slideshow)
- Final commit and tag
- Status words on every claim: **implemented**, **agent-verified**, **pending owner review**. Nothing is "accepted" unless the owner said so. Audio is always `pending owner review`.

## 11. Autonomy and recovery rules

- Decide, log (decision, options, reason), continue.
- Tool failure (npm, Playwright, headless GL): retry twice with a short wait, switch route (see 14.1 flags, alternative browser channel, software rendering), log it, re-check at the next milestone.
- Stuck on one problem more than 45 minutes: write down what was tried, choose the fallback or cut the item, move on.
- Max 3 attempts per module at the same stage, then simplify the design and log it.
- Never force-push, rewrite history or delete sources. Kill processes by PID only.

## 12. Reviewer rubric

The Reviewer is a **fresh-context agent** every time. It receives: this rubric, `STYLE_BIBLE.md`, the approved boards (and owner refs if any), the captures (contact sheet plus originals), and `checks.json`. It does not receive the author's explanations.

Prefer **paired comparison** ("which is better and why") when judging variants or before/after. For gates, also score each axis 1-10 with one or two sentences of specific evidence:

1. **Board match** (silhouette, proportions, palette vs approved board)
2. **Readability** (threats, pickups, hero, hazards parse at a glance; silhouette test holds)
3. **Lighting and colour harmony** (single key direction, palette discipline, no default-material look)
4. **Depth and composition** (layer separation, fog and scale cues, framing)
5. **Motion feel** (from frame sequences: anticipation, follow-through, weight)
6. **UI clarity and polish** (hierarchy, contrast, spacing, token consistency)
7. **Juice and finish** (feedback on hits, transitions, particles, audio cues present per audiocheck)
8. **Technical health** (`checks.json`: fps, draw calls, errors, external requests)

Gate rule: no axis below 5; average of relevant axes >= 7. Output the **top 5 defects ranked by visual impact** in the defect format. Any image the Reviewer cannot open scores 0.

## 13. Generation discipline (procedural)

- **Code is the generator.** Every visual asset is a function of parameters and a seed; record the seed and parameters in the module manifest so results are reproducible.
- **Board before build:** a new entity or environment type first appears as a Look-Dev Lab board in the approved style, is reviewed, then is used in the game.
- Keep polygon counts, texture sizes, draw calls and bundle size inside `TASK.md` budgets: instancing for repeats, geometry merging for statics, procedural textures generated once into `DataTexture`/canvas and cached.
- No external assets, no CDN, no downloaded fonts or audio. Libraries come from npm and are bundled.
- Max 3 attempts per module at one stage; then simplify.

## 14. Engine addendum — Web / Three.js (procedural)

### 14.1 Harness and environment
- Project: `npm create vite` (vanilla or TS), `three` from npm, `playwright` as a dev dependency, `npx playwright install chromium`.
- Headless WebGL: launch Chromium with software GL flags such as `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist` (verify flags during the ENV_AUDIT; they change between Chromium versions). Software GL is fine for captures. **fps is not meaningful in software GL:** measure on a real GPU in headed mode if available, otherwise report relative frame time and label it.
- Debug API on `window.__game` (only in debug/capture builds). URL params `?seed=&cam=&t=&debug=` drive captures. `preserveDrawingBuffer` in capture mode. Fixed timestep in deterministic mode.
- Serve `vite preview` on localhost for tests; `netcheck` records every request and fails on any non-localhost host.

### 14.2 Anti-slop art direction
- One key-light direction everywhere; add a rim light for silhouette separation.
- Harmonised palette (60/30/10); tint shadows toward a cool or complementary hue; avoid pure primaries.
- Organic forms via smooth blending (SDF smooth-union or metaball/marching cubes), not stacked primitives.
- Depth via fog gradient, atmospheric colour shift, layered parallax, soft blob shadows or fake ambient occlusion.
- Custom materials or shaders (fresnel rim, gradient ramps, emissive accents) instead of default grey `MeshStandardMaterial`.
- Silhouette test: fill the hero black; it must still read.
- Post-processing kept light and budgeted: bloom, vignette, mild colour grade, optional outline.
- Motion is procedural but designed: springs, easing, overlap and follow-through, anticipation before actions; no linear robotic motion.

### 14.3 Performance
Instancing for repeated objects; pool bullets, particles, floating text; no per-frame allocations; watch draw calls and shader cost; cache generated textures; keep the bundle small; pause on blur; fast restart (under 2 s) for arcade loops.

### 14.4 Determinism gotchas
Use one seeded RNG (never `Math.random()` in gameplay or generation); drive all time from the fixed-step clock in deterministic mode; capture after `step(n)` frames with the render loop settled.

## 15. Failure playbook

| Symptom | Response |
|---|---|
| Looks generic or "AI slop" | Run the 14.2 checklist; recapture; compare side by side with the approved board; revisit tokens; act on Reviewer top-5 first |
| Procedural forms look crude | Move to SDF/marching-cubes for organic parts; add rim light, ramp shading and outline; reduce detail and improve silhouette rather than adding noise |
| Reviewer scores are noisy | Recalibrate (Phase 2); use paired comparison; require specific evidence |
| Gold path breaks | Revert within 20 minutes if not obvious; re-queue |
| Headless GL fails | Try other Chromium flags or channel; fall back to software rendering; log it |
| Context compaction confusion | Re-read in the specified order; trust files over memory |
| Scope creep | Move to out-of-scope or P2; polish P0 |
| Loop stalls | Read last DEVLOG entry; pick the next TODO |

---

## 16. Definition of done

- Every P0 acceptance row passes with evidence; P1 rows pass or are documented as cut.
- Gold path passes from a clean clone; zero console errors; **zero external network requests**.
- Perf budget met and measured in the heaviest scene (method stated).
- Reviewer average >= 7 at every milestone gate; no axis below 5 on final captures.
- Audio passes `audiocheck` (numeric + spectrogram) and is labelled `pending owner review`.
- Final captures, contact sheet, timelapse, `REPORT.md` and a tagged commit exist.
- All visual and audio claims are `pending owner review` unless the owner said otherwise.

# Appendix D — Extended mode (optional)

Only if the idea card sets `MODE: extended` **and** the tools actually work in `ENV_AUDIT.md`. Procedural remains the default for gameplay-critical content and the fallback for anything that fails.

- **Concepts:** an image generator may replace the Look-Dev Lab for concept art (3 variants per subject, HTML review page, Reviewer picks, consistency pass, `selection.json` with tool/prompt/score). The lab is still built, because it verifies that the game's own rendering matches the concept.
- **3D:** generated meshes are allowed only after a 60-90 minute spike proves they rig/animate acceptably; log a `DECISIONS.md` entry.
- **Audio/assets:** free CC0/licensed assets allowed for non-defining content, logged in `Docs/LICENSES.md`.
- **Costs:** keep `Docs/COSTS.md` and `Docs/BUDGET.json`; log every paid call (UTC time, provider, endpoint, job ID, purpose, cost, output path, result); hard caps; max 3 attempts per asset; resume jobs by ID rather than resubmitting; never put brand words in prompts.
- **Secrets:** keys only in `.env` (gitignored); never printed or committed.
- **Engines:** Unity or Blender may be used in extended mode following their lessons (stop Play before refresh and prefab edits, poll compile state, Input System only, verify exports by re-importing from a copied folder). This requires their editors and MCP bridges, which are outside procedural mode.

# Appendix E — Procedural technique library

Use these deliberately; each has a purpose.

| Need | Technique |
|---|---|
| Organic bodies (creatures, dragons, blobs) | SDF smooth-union raymarching, or marching cubes over an SDF field, meshed once and cached; add rim light and ramp shading |
| Stylised shading | Gradient-ramp (toon) lighting from a code-generated 1D texture; fresnel rim; optional inverted-hull or post-process outline |
| Depth and atmosphere | Exponential height fog, colour-shifted distance fade, layered parallax silhouettes, god-ray sprites |
| Sky | Vertical gradient + sun disc + cheap scattering approximation, star field, procedural clouds (fbm noise) |
| Terrain | Multi-octave noise heightfields, ridged noise for mountains, domain warping, slope-based colour, instanced vegetation |
| Water | Fresnel blend, animated normal from two scrolling noise layers, foam from depth or noise threshold, reflection via cheap sky sampling |
| Textures | Shader-generated noise, cellular/Voronoi, gradient maps, triplanar mapping; bake to `DataTexture` once when cheap |
| Particles | GPU-instanced sprites, curl-noise motion, colour-over-life ramps, additive blending, pooled emitters |
| Trails and ribbons | Ribbon meshes with age-based width and alpha; wing-tip and projectile trails |
| Animation | Springs and damped oscillators, easing curves, overlap and follow-through, procedural wing/tail chains, secondary motion via delayed follow |
| Camera feel | Damped follow, look-ahead, FOV kick with speed, capped shake, hit-stop of 40-80 ms |
| UI art | Code-drawn SVG/canvas icons, CSS gradients, bitmap or SDF fonts drawn at start-up, consistent spacing tokens |
| Post | Bloom, vignette, colour grade curve, optional chromatic aberration at low strength; always budgeted |
| Sound | Oscillators + filtered noise + envelopes for SFX; pentatonic/modal arpeggios, pads and noise percussion for generative music with an intensity parameter |
| Variety with consistency | Seeded parameter ranges per entity; palette picked from tokens; never unconstrained random |
